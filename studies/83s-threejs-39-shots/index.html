看哪里

看哪里。注意 39 个镜头之间的转场是“切”而不是“融”——纯代码渲染没有素材重拍的成本，所以镜头可以更碎、更快。

链路拆解

核心定位用纯代码渲染替代视频模型，把“镜头”变成可版本管理的源文件。
适用场景风格化动作短片、需要逐帧精确控制与可复现的镜头段落。
必备输入83 秒片子的分镜意图；4,530 字符的提示词（公开）；8 个 agent 团队的并行调度。
标准流程分镜 → 8 个团队并行写 three.js → 逐帧渲染 → 合成音效 → 输出成片。
AI职责建模、绑定、镜头运动、渲染脚本、音效合成，全部由模型完成。
关键指标目标：83 秒成片。实际：3 小时内完成、8 个并行团队、39 个镜头、1,992 帧代码渲染（作者自述）。美元成本未披露。

为什么值得看

39 个镜头 / 1,992 帧，是这条案例真正的工程指标。按 24fps 算，83 秒约 1,992 帧——与作者给的数字吻合。这意味着每一帧都是脚本算出来的，没有一帧来自视频模型。好处是任何一帧都可以定位到具体代码行；代价是画面复杂度受限于模型写代码的能力。

8 个团队并行，说明镜头之间真的解耦了。并行不是把 8 个 agent 一起叫起来，而是要让每个团队只依赖镜头契约、不依赖别人的代码状态。能做到这一点，前提是先把美术风格、相机参数、材质规范写成可共享的约束——这部分没写进提示词，但从成片的一致性看得出来。

“3 小时”是被低估的部分。作者强调的是 3 小时出片，但没说的是这 4,530 字符提示词本身是迭代出来的。把提示词当成资产看，真正的复利在第二次、第三次做同类片子时才会出现。

可复用点与适用边界

可以迁移的

把“镜头”拆成独立可渲染单元，是并行化的前提；风格约束必须先于分工写成可共享的规格。

成立的条件

需要能逐帧渲染的管线（three.js + headless 浏览器 + ffmpeg），且团队愿意维护代码资产。

不能外推的

写实人脸、复杂布料、体积雾等效果，纯代码路线的性价比会迅速下降。
