看哪里

看哪里。看蟹壳的半透明与次表面散射——这类材质基本只能靠渲染器算，不是靠提示词描述出来的。

链路拆解

核心定位用 Blender + Python 承担建模与渲染，模型团队写代码而不是写画面。
适用场景需要真实材质、复杂光照、可信动作的短片；浏览器管线做不出质感的场合。
必备输入Blender + Python 环境、fal 云端算力、ElevenLabs 音乐音效；多个 Fable 与 Opus agent 协同。
标准流程剧本与角色设定 → agent 团队写 Blender Python → 4K 云渲染 → 音乐与音效合成。
AI职责建模、绑定、动画、渲染脚本；人给设定与终审。
关键指标目标：1 分 25 秒短片。实际：约 28,000 行代码、4K 渲染、fal 云端算力（作者自述）。美元成本与渲染时长未披露。

为什么值得看

28,000 行是这条案例的门槛。同一个团队在纯 three.js 项目里写的是几千行级别的场景脚本；到了 Blender，代码量上一个量级，因为建模、绑定、材质节点、渲染设置全都要用 Python 描述。这也意味着更高的返工成本：改一个材质参数，可能要重跑一次 4K 渲染。

退到 Blender 不是退步，是换赛道。浏览器渲染擅长图形化的、平面化的、可程序化生成的东西；一旦需要真实感材质和复杂光照，Blender 的物理渲染器更划算。判断标准应该是“质感是否可被代码近似”，而不是“是不是纯代码”。

多 agent 协作在这里的作用是分工，不是加速。Fable 与 Opus 的 agent 团队分担建模、动画、渲染脚本，人负责角色设定与终审。代码量越大，分工带来的接口成本越高——这正是 28,000 行背后不常被提及的成本。

可复用点与适用边界

可以迁移的

选链路先看质感上限：能被代码近似的走浏览器，需要真实材质的走 Blender。

成立的条件

需要云渲染预算与版本管理；Blender 工程的返工粒度比网页工程粗。

不能外推的

28,000 行不代表效率提升，只是复杂度转移；没有渲染时长与成本，无法评估单位产出。
